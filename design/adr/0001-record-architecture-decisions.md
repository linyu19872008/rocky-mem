# ADR-0001：记录架构决策

- 状态：已采纳
- 日期：2026-11-24
- 决策者：维护者

## 背景

本项目在早期就做了几个几乎不可逆的选择：拆成两张表、存储引擎、检索 tokenizer、语言策略、双数据库支持。这些选择从代码里能看出**结果**，但看不出**被否决的选项**——而被否决的部分不会留下任何痕迹。

项目计划开源。外部评审最常问的是"为什么这么做"，而诚实的答案往往是"我们考虑过三个方案，其中两个因为你看不到的原因更差"。

## 决策

采用 Michael Nygard 的轻量架构决策记录（ADR）：一个决策一个文件，编号，一旦采纳不再修改。

每条 ADR 只有三段实质内容：

- **背景**：起作用的力，包括不显然的约束
- **决策**：我们做什么，直说
- **后果**：得到什么、**放弃什么**、什么情况下应当重新审视

"放弃什么"是必填段。只列收益的 ADR 是新闻稿，不是决策记录。

决策被取代的方式是写一条新 ADR 引用旧的，旧文件永不修改。

## 后果

**得到**：推理能活下来；评审者评估权衡而不是猜；新贡献者能知道什么不要再提。

**放弃**：每个架构变更多一个文件，而且要在最没有时间的时候写。

**重新审视的条件**：ADR 超过约 30 条、自身成为维护负担时，应当合并而不是废弃。

## 备选方案

- **只写设计文档**：`DESIGN.md` 描述当前状态，并随状态改写。它无法呈现被否决的方案，因为被否决的东西不产生文件。
- **靠 commit message 和 PR 描述**：精神上正确，实践上不可检索——没人会为了搞清一张表为什么被拆而翻四百个提交。
- **什么都不写**：默认做法。也是代码库里出现"没人敢改的决策"的方式。
