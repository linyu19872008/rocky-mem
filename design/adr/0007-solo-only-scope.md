# ADR-0007：0.x 只交付单人模式，团队模式推迟

- 状态：已采纳
- 日期：2026-11-26
- 决策者：维护者
- 相关：[ADR-0005](0005-technology-stack.md)（Go 选型）、[ADR-0006](0006-two-database-strategy.md)（双库策略）

## 背景

团队模式原本是两条架构决策的重要理由：它让 Go 的「单二进制服务两端」成为主要卖点（ADR-0005），也让 PostgreSQL 从「可能用得上」变成「必须支持」（ADR-0006）。

但把单人核心真正做出来之后，情况变了：

1. **核心还不扎实。** 投喂把长文档压进 `fix_md`（没有 `source`/`chunk`）、冲突只能并排看不能裁定、没有性能基准、审核队列没有键盘操作。这些直接影响每天都用的人。
2. **Team 不是「打开一个开关」，是另一个产品。** 它至少要：真实鉴权（`membership` 生效、多 token）、多写者并发（advisory lock、幂等键、冲突重试）、PG 备份恢复、租户隔离与审计边界。每一项都是周级工作量，且全都没验证过。
3. **含糊的「两种模式」已经在产生误导。** README 写着「Two modes, one binary」，schema 里躺着 5 张没人读的表，`scope='team'` 被接受但永远查不到东西。读者会以为团队模式可用。

一个人的工具，先把一个人的手感和可靠性做好，比同时承诺两种形态更值钱。

## 决策

**0.x 只交付单人模式（Solo）。团队模式是明确的未来规划，不在当前实现范围。**

具体含义：

1. **不实现鉴权。** 单人模式只有隐式本地用户 `app_user(1,'local')` 与单枚 Bearer token。不做登录、不做多 token、不做 `membership` 授权。
2. **保留「缝」但不接线。** `app_user` / `team` / `membership` / `api_token` / `setting` / `idempotency` 六张表保留在迁移里，**但代码不读不写其中三张权限表**。保留的理由是避免日后做破坏性迁移，不是因为它们现在有用。
3. **`scope='team'` 是死值。** 读路径只查 `global` 与当前 `project`；写入显式给 `team` 会被存下来，但永远检索不到。文档必须写明这一点，不能让 agent 或人选它。
4. **PostgreSQL 保留，但定位降级**：它是「更喜欢用 PG 的单人用户」的替代存储后端，**不是共享服务**。`pg_advisory_xact_lock`、并发压测、PG 备份恢复都不做。
5. **文档口径统一**：任何把团队模式描述成「可用」的措辞都要改掉。团队相关的能力一律标 `Planned`。

## 后果

**得到：**

- 精力集中在一个形态上；「核心功能做扎实」有了明确的对象。
- 安全承诺变诚实：单人模式的隐私来自「数据只在你机器上」，这条现在是真的，不再需要「团队模式靠不实现某些视图来兑现」这种软保证。
- 表面变小：没有半成品鉴权，就没有半成品鉴权的漏洞。
- 未来做团队模式时，起点是干净的——今天不做的那些并发工作不会因为忽略而腐坏，只会因为没做而缺席。

**放弃：**

- **PostgreSQL 的价值收窄。** 它不再解决「多人共享」，只剩「换个存储引擎」。ADR-0006 的很多论证（团队部署、连接池、advisory lock）暂时悬空。
- **六张预留表是死重。** 读 schema 的人会问「这些表为什么不用」，答案是「为未来留的缝，现在没接」。已写入 `DESIGN.md` §15.1。
- **假设被推迟而非验证。** 「多人可用」这件事没有证据。若真做，起点是零。
- **`scope` 有四种值但只有三种能用。** 这是设计债，靠文档与校验提示来兜，不是靠类型系统。

**重新审视的条件**（足够具体，避免凭感觉重启）：

1. 有一个真实团队明确要求共享同一个知识库，且愿意承担部署与运维；或
2. 同一个人需要在两台以上机器上读写同一个库；或
3. 单人模式的核心缺口（语料层、冲突裁定、性能基准）已全部关闭，且有富余产能。

满足任一条件时，按顺序做：鉴权 → 并发控制（advisory lock + 幂等键）→ PG 备份 → 并发压测。**不要跳过压测。**

## 备选方案

- **现在就做团队模式**：否决。核心功能未扎实，此时做鉴权等于在漏水的船上装桅杆。
- **把团队相关的表和 `team` scope 一起删掉**：否决。迁移成本真实，而六张表的维护成本接近零；留缝比日后破坏性迁移便宜。但必须写清「预留、未接线」，否则缝会变成误导。
- **维持「两种模式」的模糊表述**：否决。这是当前文档最大的失真来源——读者会按团队模式规划部署，然后发现没有鉴权。
- **把 PostgreSQL 一起推迟**：否决。它已经能跑通一致性套件，删掉是浪费；只要不把它说成「共享服务」即可。
