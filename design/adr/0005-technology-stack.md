# ADR-0005：采用 Go，单二进制支撑双形态

- 状态：已采纳
- 日期：2026-11-24
- 决策者：维护者
- 取代：[ADR-0003](0003-sqlite-first-with-portable-schema.md)

## 背景

需求在 v0.3 之后发生了实质变化，三条：

1. **未来要支持多人使用**——不再是"一个人一台机器"。
2. **有性能要求**——但从未量化。
3. **数据库要支持 PostgreSQL**，并曾要求 MySQL（见 [ADR-0006](0006-two-database-strategy.md)）。

这三条不是同一个问题。第 3 条决定了存储层必须抽象；第 1 条决定了部署形态必须从"本地进程"扩展到"长期运行的服务"；第 2 条则最容易误导——它听起来像语言题，实际不是。

先量化，再选语言：

| 规模 | 检索 QPS（每人每 5 分钟一次） | Python 单 worker 余量 | Go 单进程余量 |
|---|---|---|---|
| 500 人 | ~2 | 99.9% | 99.99% |
| 5 000 人 | ~17 | 99.4% | 99.9% |
| 50 000 人 | ~170 | 94% | 99.4% |

一次 `mem_search` 的成本构成约为：HTTP 解析 0.1 ms + SQL 2 ms + 装配 1 ms + 序列化 0.3 ms。语言只影响其中最前面那 0.1～1 ms 的部分。

**结论：在五万人以内，语言不是瓶颈，差距不到 5%。** 真正的瓶颈依次是：每次请求的 SQL 条数、索引是否命中、连接池与数据库连接上限的匹配、写事务的冲突检测成本、以及（P3 的）向量重排。这些都与语言无关。

同时，Python 方案还有一个此前的隐性前提已经失效：`stdlib only` 这条原则本身站不住（详见下方"关于撤回 stdlib-only"）。

## 决策

**采用 Go，单一二进制，两种运行形态由 DSN 切换。**

- 单人模式：`sqlite://`，嵌入式，本地 loopback + token。
- 团队模式：`postgres://`，连接池 + 乐观锁 + advisory lock。

具体选型：

| 关注点 | 选型 |
|---|---|
| 语言 | Go 1.25+（跟随最近两个 minor 版本） |
| HTTP | 标准库 `net/http`（含 1.22 增强路由）+ 少量中间件 |
| 数据访问 | `database/sql` + `sqlc` 生成的双方言代码 |
| 驱动 | `modernc.org/sqlite`（纯 Go）、`pgx/v5` |
| 迁移 | `golang-migrate` + `embed.FS`，两套方言文件 |
| CLI | `cobra` |
| 日志 | 标准库 `log/slog` |
| MCP | 官方 `modelcontextprotocol/go-sdk` |
| 前端 | TypeScript + Vite + React + FormatJS，产物 `go:embed` 进二进制 |

### 为什么是 Go

按重要性排序，**没有一条是"快"**：

1. **单二进制同时服务嵌入与服务端。** `brew install` 或下载一个文件就能跑单人模式；同一个文件放进 distroless 容器就是团队服务。Python 在嵌入端要 Python 运行时与 venv，在服务端要进程管理；Node 要 Node 运行时。这是唯一一个两端都不将就的选择。
2. **`database/sql` + `sqlc` 给三种方言提供统一的、编译期校验的存储层。** 这恰好匹配已定的"不用 ORM、手写 SQL"原则。Python 侧没有对等物——`sqlite3`（同步、`?`）、`psycopg`（`$1`）、`aiomysql`（`%s`）是三套 API、三套异常、三套占位符。
3. **多人服务是长期运行的进程。** 连接池、优雅关停、健康检查、`-race`、`pprof` 在 Go 里是一等公民或内建。
4. **Python 的核心优势被部署形态抵消。** PDF 解析是一次性离线作业，embedding 在服务端本来就该外置成 HTTP 服务。这两项恰好是 Python 最强、Go 最弱的地方，而它们在团队模式下都不是热路径。

### 关于撤回 `stdlib only`

v0.3 的 `DESIGN.md` 写过"运行时只用标准库"。这条是从更早的个人脚本语境继承来的，用错了场景。

手写 HTTP 服务意味着自己实现 SSE 重连、Range 请求、静态文件缓存头、请求体限制、并发与背压、优雅关闭——800～1200 行看起来正确、实际处处细微 bug 的代码，而且是唯一暴露给浏览器的安全敏感面。

**正确的原则不是"零依赖"，是"少量、无聊、可审计的依赖"。** 这已经是 Go 的优势区：标准库覆盖 HTTP、JSON、日志、模板、embed、测试，第三方只需 `sqlc` 生成代码 + 驱动 + `cobra` + `toml`。

## 后果

**得到：**

- 单人模式零安装摩擦（单文件），团队模式零运行时依赖（单文件）。
- 存储层两类方言共用一套接口，且 SQL 分开评审。
- 并发安全有编译器与 `-race` 兜底，这对多写者路径尤其重要。
- 冷启动到首个 MCP 响应约 150 ms（对比 Python 的数秒级 import + venv 查找）。
- 同一份代码库同时是 CLI、守护进程、MCP 服务器。

**放弃：**

- **开发速度。** P0 从约 1 周变成约 3 周。这是本决策最真实的价格，一次付清。
- **Python 的文本与 ML 生态。** 分词、PDF、embedding 都要换方案或外置。已接受的权衡。
- **REPL 式的探索。** 数据清洗规则的试验会比 Python 笨拙，缓解手段是写好表驱动测试。
- **cgo 的不确定性。** 纯 Go 的 SQLite 驱动是否编译了 FTS5 **必须实测**；若不含，退路是 `mattn/go-sqlite3`（cgo，需各平台构建机或 Docker 构建）。
- **抽象税前置。** 为了让两个后端行为一致，P0 就要写两套 SQL 与一致性套件。

**重新审视的条件**：若 Go 1.2x 之后仍无法在生产可用的纯 Go 驱动里拿到 FTS5，且 cgo 构建链成为发布阻塞，则应重新评估"SQLite 侧改用其他全文方案"或"单人模式也要求 PostgreSQL"。

## 备选方案

- **Python**：开发最快、生态最全、MCP SDK 是一方维护。否掉它的不是性能，是**团队模式的运维摩擦**与**驱动不统一**。若项目坚持"三个月内必须上线单人版"，Python 仍是合理选择，代价是多人化时重写存储层与部署。
- **TypeScript**：单一语言覆盖前后端，官方 MCP SDK 最成熟，`npx` 安装体验最好。否掉它的原因是服务端长期运行的运维习性、SQLite FTS5 依赖原生模块（`better-sqlite3` 或 `node:sqlite` 的编译选项），以及没有 `sqlc` 的对等物。
- **Rust**：单二进制与运行时性能最优。否掉它的是 P0 三周的约束（Rust 下大概率翻倍）与贡献者池小一个数量级，而其优势在这个负载上用不到。
- **维持 Python 并接受未来重写**：被明确否决。存储层抽象、身份模型、并发控制一旦在有数据的库上重构，成本是事故级的。
