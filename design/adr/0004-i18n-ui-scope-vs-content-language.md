# ADR-0004：界面本地化与内容语言必须分开

- 状态：已采纳（§7 文档语言策略于 v1.0 修订）
- 日期：2026-11-24
- 决策者：维护者

## 背景

"支持中英文"把两个互不相关的问题捆在了一个词下面。

**界面本地化**是有限且可穷举的：几百条字符串、一个语言开关、复数规则、日期格式。它可解，质量在首屏就能看见。

**内容多语言**是无界且用户生成的。这个库里会有中文笔记、英文报错、以及混着两种语言的条目——"跑 `kubectl rollout restart` 之后 Pod 起来了"。它无法穷举，而最直觉的应对——把所有内容翻译成一种标准语——会让每条事实出现两个版本，各自带自己的证据链和可信度。

项目还计划开源，这固定了另外两条约束：默认语言必须是 `en` 而不是作者的母语；仓库必须让不读中文的贡献者能参与。

## 决策

### 两个问题用两种办法解决

| | 界面本地化 | 内容语言 |
|---|---|---|
| 手段 | 消息目录 + ICU MessageFormat | `lang` 标记 + 跨语言检索 |
| 内容翻译 | 不适用 | **永不执行** |
| 责任人 | 维护者与译者 | 写下它的人 |

### 界面规则

- 支持 `en`、`zh-CN`。兜底 **`en`**。
- 解析顺序：`?lang=` → 服务端 `setting.locale` → `Accept-Language`（BCP-47 截断匹配）→ `en`。
- 解析发生在**服务端**，首屏就带正确的 `<html lang>` 与正确的消息目录。不存在错误语言的闪烁。
- 用 ICU MessageFormat，不用字符串拼接，不用自造的复数助手。
- 存入数据库的是英文码（`trust='contested'`），展示标签在表现层翻译。任何展示字符串都不进数据库。
- API 返回 `{code, params}`，绝不返回本地化文案。CLI 自己从 `ROCKYMEM_LANG` / `LC_ALL` / 系统界面语言解析。
- MCP 工具名、参数名、描述、上下文包小标题永久英文，不做本地化。

### 内容规则

- 每条内容行带 `lang`（BCP-47，另有 `und` 未定、`mul` 真正混合）。入库时按字种比例检测，作者可覆盖。
- 内容在写入、存储、读取时都不翻译。
- 跨语言检索靠**受控双语术语表**（`term` 表，由 `data/seed/term-map.zh-en.yaml` 播种）：查询词按 0.7 权重扩展出译词，保证原语言命中优先。机翻不用于扩展——它引入语义漂移（`内存` → memory 还是 RAM？）并污染召回。
- 一切文本在 hash 与入库前做 NFC 归一化。

### 文本检索：一个索引，trigram tokenizer

`search_doc` 在 SQLite 侧用 `tokenize='trigram'`，在 PostgreSQL 侧用 `pg_trgm` + `ILIKE`。

理由不是语言，是**语料**。这个库密集出现精确字符串：`kubectl rollout restart`、`Xid 69`、`bge-m3`、`ERR_EVIDENCE_REQUIRED`、`/pkg/config/reload.go`。子串匹配正是处理它们正确的原语，同时无需词典即可处理中文，且不引入依赖。词干化 tokenizer 与中文分词器各自解决半个语料，同时伤害另一半。

接受的代价与缓解：

| 代价 | 缓解 |
|---|---|
| 无词干：`config` ≠ `configuration` | 术语扩展；作为刻意取舍接受 |
| 少于 3 字符的 token 不入索引 | 查询含短 token 时并入 `LIKE '%x%'` 兜底 |
| trigram 上的 BM25 偏噪 | 只作候选生成；最终排序规则化，加"标题逐字命中"加权 |

## 后果

**得到：**

- 界面可翻译而不动存量数据；加一种语言不迁移任何东西。
- 一个人的中文笔记和另一个人的英文笔记都是一等公民；不强制任何标准语。
- 上下文包对 prompt 缓存与评测是语言稳定的，正文保持原样。
- 没有 locale 信号的 agent 也能拿到完整一致的行为。

**放弃：**

- **跨语言检索在 P3 之前只做到一半。** 在向量出现前，中文查询只能通过受控术语表命中英文条目，表外的领域词汇无法桥接。已记录在 `DESIGN.md` §15。
- **跨语言冲突检测只做到一半。** `symptom_key` 只有存在语言中立 token（报错码、路径、工具名）时才能跨语言归一。
- **没有词干化。** 真实存在，偶尔会丢一次匹配。
- **2 字中文查询不走索引。** 正确但是扫描。
- **两种文档语言是维护负担。** 通过收窄承诺范围缓解（见 §7）。
- **界面依赖构建步骤。** 前端需要 Node 构建；运行时不需要（产物随二进制发布，`web/dist` 不入库）。

**重新审视的条件**：若出现无构建步骤的中文分词器单依赖，或评测显示 trigram 召回是主要质量问题而非舍入误差。

## 备选方案

- **单一标准语，写入时翻译**：每条事实两个版本、两条证据链、两种可信状态，且翻译可能悄悄改变解法的含义。因正确性被否，不是因为成本。
- **`unicode61` + porter 词干**：英文好，中文不可用。
- **中文分词（jieba 等）**：依赖、英文处理差、且会切碎标识符——语料里最值钱的东西。
- **两套并列索引（按语系）**：正确但索引维护翻倍，且跨索引比分数无意义，合并逻辑仍需自己的规则。

## §7 文档语言策略（v1.0 修订）

初版规定"所有文档英文"。实际使用中这条对设计文档不成立：设计文档的读者是维护者，用母语表达权衡更精确、更快。

修订为：

| 类别 | 语言 | 理由 |
|---|---|---|
| **设计层**：`DESIGN.md`、`schema.md`、`adr/**` | **中文** | 读者是维护者；权衡与取舍需要精确表达 |
| **契约层**：`../docs/mcp-tools.md`、`../docs/error-codes.md`、`api/openapi.yaml` | 英文 | 读者是外部贡献者与第三方客户端；标识符必须与代码一致 |
| **规范层**：`../docs/i18n.md`、`../docs/i18n-glossary.md` | 英文 | 规范性文本；术语表本身即中英对照 |
| **工程层**：`README.md`、`CONTRIBUTING.md`、`SECURITY.md`、`CHANGELOG.md`、代码注释、commit message | 英文 | 开源协作的公共语言 |
| `README.zh-CN.md` | 中文 | 维护中的翻译 |

划分依据不是"哪个更重要"，而是**读者是谁**。这条规则写进 `README.md`，作为文档索引的一部分。
