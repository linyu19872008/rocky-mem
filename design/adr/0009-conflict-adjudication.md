# ADR-0009：冲突裁定

- 状态：已采纳
- 日期：2026-11-27
- 决策者：维护者
- 相关：[ADR-0002](0002-split-memory-and-experience-tables.md)（经验台账）、[ADR-0007](0007-solo-only-scope.md)（只做单人）

## 背景

系统能检测冲突，但不能判断谁对：

```
新经验写入 → 计算 symptom_key → 同簇已有条目且 fix_hash 不同
           → 新建 conflict_group → 两条都转 contested
```

`contested` 是**一个问题**，不是一个结论。问题在于它当时没有像样的答法。

旧实现只有两个动作（`keep` / `archive_all`），四个缺陷：

1. **语义错位。** `keep` 把对手置为 `archived`。归档的含义是「不再流通（重复/过时）」，而冲突裁定通常是「同样症状下两个解法互斥，我选这个」——对方是被**证伪**，不是被归档。两者的检索含义也不同：`falsified` 权重 0.1 且仍在库里可查，`archived` 直接不参与检索。
2. **最常见的结局做不了。** 真实冲突大多不是「一对一错」，而是「两条都对，适用条件不同」（K8s 版本、文件挂载 vs API 读取、单机 vs 集群）。界面逼人在「选一个」和「都归掉」之间二选一，两个都不诚实。
3. **没有理由。** 只留一行 `review:resolve:keep` 审计。半年后看到一条 `archived`，没人知道它是被证伪、被合并，还是重复。
4. **归档不删索引。** `ReviewReject` 改了 `trust` 却没调 `DeleteSearchDoc`，检索靠 `filterVisible` 兜住所以用户看不见，但 `doctor` 的对账会报漂移——这是设计文档 §5.4 写明的规则，实现漏了。

冲突还会**持续产生**：agent 的 `mem_feedback(wrong)` 也会把条目推进 `contested`。不给人裁定工具，这个状态就只进不出。

## 决策

**裁定是人的动作，不是 agent 的。** 五个动作，记录追加，不许覆盖。

| 动作 | 语义 | 状态变化 | 硬约束 |
|---|---|---|---|
| `adopt` | 一条对，其余错 | 胜者 → `active`；其余 → **`falsified`** | 理由必填；胜者无证据时返回 warning |
| `split` | 都对，条件不同 | 两条都 → `active` | 四条条件全必填（各自 applies + 各自 invalid）；两边的 applies 不能相同；组必须恰好两条 |
| `reject_both` | 两条都是伪知识 | 全部 → `falsified` | 理由必填 |
| `defer` | 证据不足 | 保持 `contested` | `review_after_days > 0` |
| `reopen` | 旧裁定被推翻 | 全部 → `contested` | 理由必填 |

配套决定：

1. **`conflict_resolution` 表，append-only。** 每次裁定一行；同一组可以裁多次（复开后再裁），历史可读。`LatestResolution(group)` 给出当前结论。
2. **建 `link` 表。** `split` 写双向 `complements`，为将来的 `merged_from` / `derived_from` 留位。`link` 是关系，不替代证据。
3. **`split` 的条件写回条目**（`applies_when` / `invalid_when`），同时重写检索行——否则条件只存在裁定记录里，检索用不上。
4. **裁定不进 MCP。** 六个工具不变；agent 只能 `mem_feedback` 上报，不能裁决。给 agent 盖章权会直接毁掉可信度模型。
5. **`falsified` 是可查的否定**：仍可 `mem_get`、仍在审计里，只是不参与检索。
6. **检索包显式标注未裁定冲突**：`contested` 条目开头写一行 `> Contested — not adjudicated`，并列出对方 uid；同组条目相邻渲染（`split` 的对必须被当成一对读）。
7. **顺手修掉归档不删索引的缺陷**，`setTrust` 统一处理索引生命周期。

## 后果

**得到：**

- 冲突有出口：五种结局覆盖了真实场景，最常见的那种（条件不同）终于可以诚实表达。
- 裁定留下理由，`mem_get` 能看到这组的全部裁定历史。
- 检索不再把「有争议」伪装成普通建议。
- `falsified` 与 `archived` 的语义分开后，「这条被证伪过」变成可查询的事实。

**放弃：**

- **`split` 需要人写条件。** 写不出具体、互斥的条件时只能 `defer`——这是刻意的，糊一句「取决于条件」比不裁更糟。
- **一次只能处理两条。** 三成员以上的组要求先两两合并，否则 `split` 拒绝。多边裁定没有好的语义。
- **`keep` 语义变更。** 旧调用（`action:"keep"`）不再被接受，失败方由 `archived` 变为 `falsified`。这是行为变更，写进 CHANGELOG。
- **Web 只做裁定、不做复开**（复开走 CLI/HTTP）。复开是低频动作，为它再做一个界面不划算。
- **裁定没有权限模型。** 单人模式没有「谁可以裁」的问题；团队模式落地时需要重看。

**重新审视的条件**：若冲突组经常出现三个以上成员，说明 `symptom_key` 聚得过宽，应先修聚簇而不是加多边裁定。

## 备选方案

- **让 LLM 自动裁定**：否决。裁定需要观察事实，模型没有；它会给出自信的随机答案，而且无法被追责。
- **维持 `keep` / `archive_all` 两个动作**：这就是现状，问题是它逼人在两个不诚实的选项里选。
- **把裁定结果只写审计**：可查但不可展示、不可查询「这条为什么是 active」，也存不下 `review_after`。
- **裁定时允许顺手编辑正文**：会让裁定和编辑混在一个事务里，失败时难以回滚。先只允许改 `applies_when` / `invalid_when`——那是 `split` 的最小必要面。
- **把裁定暴露成 MCP 工具**：否决，理由见决策 4。
