# ADR-0002：记忆与经验拆成两张表

- 状态：已采纳
- 日期：2026-11-24
- 决策者：维护者
- 取代：v0.2 设计中的单表 `entry(kind=…)` 方案

## 背景

早期草稿把两类知识放进一张多态 `entry` 表，用 `kind` 列区分。那是常规做法，在这里是错的，原因有四条，而且是在推演写语义时才浮出来的。

**1. 两者性质不同。**

记忆是**状态**：事物现在是什么样——包管理器、回复语言、这个仓库用 Argo 部署。经验是**台账**：某问题在某种条件下被某种方式解决过的陈述，且带证据。状态只有一个当前值，会被编辑；台账累积，永不被改写。

放进一张表就会把一套写语义强加给两者。都按 upsert 处理，经验历史被覆盖，违反只追加；都按追加处理，偏好会堆出互相矛盾的副本且无法指明哪个是当前值。

**2. 字段重叠率约 40%。**

```
记忆独有    mem_key, mem_type, pinned, priority, superseded_by, lineage            (6)
经验独有    exp_type, symptom, symptom_key, root_cause, fix_md, fix_hash,
            applies_when, invalid_when, outcome, confidence, trust, conflict_group,
            cost, verified_by, t_verified                                         (15)
共享        id, uid, scope, scope_ref, title, lang, sensitivity,
            actor_id, rev, created_at, t_last_used, use_count                     (10)
```

合表的列数是 31，任意一行平均 21 个 NULL。一半的列注释会写成"仅当 kind = experience 时有效"。

**3. 访问路径不同。**

记忆在会话开始时被无条件读取，按 scope 过滤，按 `pinned`/`priority` 排序；经验按文本查询读取，按 `trust` 过滤。前者需要复合 B 树索引，后者需要全文索引。合表时两套都要在每次写入时维护，而每次读取只用其中一套。

**4. 不同语料的全文分数不可比。**

BM25 的 IDF 项依赖各自语料。800 行表与 30 000 行表给出的分数不在同一量纲，跨类型"统一排序"是伪精度，会产出看起来合理的错误顺序。拆表让这个错误在结构上无从发生。

## 决策

两张表，`memory` 与 `experience`，共享一个基底：

- 共享基底：`raw`（不可变证据）、`evidence`（多态指针）、`tag`、`audit`，以及同一条写入漏斗。
- `memory` 通过部分唯一索引 `(scope, scope_ref, mem_key) WHERE status='active'` 实现就地更新语义；编辑新增一行并保留稳定 `lineage`，旧行转 `superseded`。
- `experience` 只追加；`trust` 在 `proposed → active → contested | stale | falsified → archived` 之间流转。
- 跨类型浏览由只读视图 `v_feed` 承担，避免两张表变成两个互不相干的系统。
- 写入默认值刻意不同：记忆直接发布，经验进 `proposed` 等待审核。

## 后果

**得到：**

- 每条写入路径恰好有一套合理的语义。
- 审核闸门可以同时对经验严格、对记忆廉价——合表时做不到。
- 索引各司其职；"一个当前值"由数据库强制而非应用约定。
- 不存在无意义的跨语料排序。
- 日后加第三类知识意味着加一张表，而那时新类型的差异必然更大，这是对的。

**放弃：**

- **多态 `evidence.owner_id` 与 `tag.owner_id` 无法建外键。** 缓解：唯一写入路径、`purge` 在同一事务删主体与证据、`ON DELETE RESTRICT` 保护反方向、`doctor` 巡检孤儿。
- **分诊后两条写入分支**，约一百行重复的闸门管道。为清晰度接受。
- **跨类型全文排序**在设计上被禁止。若真出现需求，答案是一个显式的混合分段，而不是共享索引。
- **引用命名空间分裂**。带前缀的 ULID（`m_`、`e_`）保证可读性。

**重新审视的条件**：出现第三、第四种类型，且字段与现有两者重叠超过 70%。那时多态是真的，正确的形状是单张 `entity` 表加各自的类型侧表。

## 备选方案

- **单张 `entry` 表 + `kind`**（早期草稿）：见背景。
- **两张表 + 物化联合表**：跨类型读更快，但多了一个会漂移的第二真相。在本规模下视图成本可忽略。
- **单表 + 每类型一个 JSON 负载**：灵活一周，不可查询一辈子——`mem_key` 上没有部分索引，`trust` 上没有约束，`symptom_key` 上无法建索引，每个查询都退化为全表扫描。
- **每类型一个数据库**：丢失跨类型出处，运行面翻倍且无收益。
