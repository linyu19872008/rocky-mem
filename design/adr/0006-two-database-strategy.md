# ADR-0006：只支持 SQLite 与 PostgreSQL，且不用 tsvector

- 状态：已采纳
- 日期：2026-11-24
- 决策者：维护者

## 背景

需求是"数据库以后要支持 MySQL、PostgreSQL 等"。拆开看，这里有两个独立决定：

1. 支持几种数据库？
2. 用 PostgreSQL 的哪套全文检索？

第 1 个决定的成本被严重低估。第 2 个决定的后果比第 1 个更深。

### 支持多库的真实成本不是 SQL 方言

把现有的 schema 摊到三个数据库上，会撞到三处硬伤和一处隐形杀手：

| 能力 | SQLite | PostgreSQL | MySQL 8 |
|---|---|---|---|
| 部分唯一索引 `WHERE status='active'` | ✅ | ✅ | ❌ 需生成列变通 |
| 精确子串检索（标识符、报错码） | ✅ FTS5 trigram | ✅ `pg_trgm` | ⚠️ ngram 分词，明显更差 |
| BM25 排序 | ✅ `bm25()` | ✅ `ts_rank_cd` | ❌ 无 |
| 默认大小写敏感性 | 敏感 | 敏感 | ❌ 默认不敏感 |

**隐形杀手**：MySQL 默认排序规则 `utf8mb4_0900_ai_ci` 大小写不敏感。而我们的 `uid` 是 Crockford Base32（含大小写）、`hash` 是十六进制、`mem_key` 是小写约束。不改 `utf8mb4_bin`，会得到**随机发生的唯一性失效**——上线三个月才炸的那一类。

**部分唯一索引**是记忆表存在的理由（[ADR-0002](0002-split-memory-and-experience-tables.md)）。在 MySQL 上只能靠生成列：

```sql
active_key VARCHAR(255) AS (IF(status='active', CONCAT(...), NULL)) STORED,
UNIQUE KEY ux_memory_current (active_key)
```

语义可行（唯一索引允许多个 NULL），但意味着**同一张表有三种 DDL 写法**，schema 不再是一份。

**真正的成本还有第二个来源**：并发语义。单用户版最巧妙的设计是"单写者队列 + `BEGIN IMMEDIATE`"。多用户下这个前提消失，写路径必须重写成乐观锁 + advisory lock（或等价物）。三个数据库的锁原语各不相同，测试矩阵乘以三。

## 决策

### 决策一：只支持 SQLite 与 PostgreSQL

| 数据库 | 定位 | 承诺 |
|---|---|---|
| SQLite | 单人/小团队的嵌入式模式 | 一等，全功能 |
| PostgreSQL | 团队部署的唯一生产库 | 一等，全功能 |
| MySQL | **不支持** | —— |

MySQL 不进入核心，理由具体而非偏好：

1. 部分唯一索引需要生成列变通，schema 三分叉。
2. 全文检索无 BM25、无相似度算子，而整个检索设计建立在"精确字符串 + 子串匹配"上。
3. 默认 collation 是地雷，且不显式规避就会静默出错。
4. 它把每个集成测试乘以三，**永久性**。
5. 提出这个需求的通常是"技术选型想象"，而不是某个具体客户的硬约束。

若日后确有客户要求，做法是**社区维护的适配器**，而不是并入核心。届时另写 ADR。

### 决策二：PostgreSQL 用 `pg_trgm`，不用 `tsvector`

这是本 ADR 最有争议的部分。它反常规，但从已锁定的原则直接推出：

> [ADR-0004](0004-i18n-ui-scope-vs-content-language.md)：选 trigram 是因为**语料性质**——记忆库里最值钱的是精确字符串。词干还原反而伤害精确性。

`tsvector` 提供的恰好是我们**主动拒绝**的能力（词干化），却要额外的语言词典（中文需 `zhparser`，多数托管 PostgreSQL 不提供）。

而 `pg_trgm` 的 GIN 索引**支持前置通配符的 `ILIKE`**，语义与 SQLite 的 trigram `MATCH` 等价：

| 能力 | SQLite | PostgreSQL（`pg_trgm`） |
|---|---|---|
| 英文精确子串 | ✅ | ✅ |
| 标识符 / 报错码 | ✅ | ✅ |
| 无词典的中文 | ✅（trigram） | ✅（trigram） |
| 需要扩展 | 无 | `pg_trgm`（托管 PG 普遍自带） |
| 词干化 | ❌ | ❌ |

代价是两边都没有词干化。这是刻意的：`config` 匹配不到 `configuration` 是已知限制，由术语扩展缓解，而不是引入一个会切碎 `ERR_CONN_REFUSED` 的分词器。

`zhparser` 存在时作为**可选增强**：仅对 2 字及以上中文查询追加一条 `tsvector` 路径并与 `ILIKE` 结果合并，由 `doctor` 探测，不由迁移强建。

## 后果

**得到：**

- schema 只有两种写法，差异集中在 7 个点上（`schema.md` §4 逐条列出），可逐条评审。
- 两个后端的检索语义一致（都是 trigram 子串），只是打分模型不同。
- 测试矩阵为 2，而非 3。
- 不引入任何"最低公分母"式设计让步——部分唯一索引、只追加语义、`ON DELETE RESTRICT` 全部保留原样。

**放弃：**

- **两套 SQL。** `db/queries/{sqlite,postgres}/` 分开维护，约 15～20 条核心查询。这是显式成本，且换来了"差异被评审"而非"差异被抽象掩盖"。
- **跨后端统一的排序分数。** `bm25()` 与 `similarity()` 不可比。缓解手段是"分数只在单次查询内有效"这一接口约束，加上最终排序规则化。
- **2 字中文在 PostgreSQL 大表上不走索引。** `pg_trgm` 与 FTS5 trigram 都需要 ≥3 字符。5 万行内可接受；更大需 `zhparser`。已记录为限制。
- **开发者的 MySQL 习惯**。明确说不，并给出理由。

**重新审视的条件**：

- 若出现一个付费客户，其基础设施硬性要求 MySQL——那时写新 ADR，评估做社区适配器。
- 若评测显示无词干化造成显著召回损失（例如 `recall@10` 因形态学匹配下降超过 10 个百分点）——那时评估混合方案（`tsvector` 用于英文、`pg_trgm` 用于标识符与中文），成本约 3 天。

## 备选方案

- **支持三库**：见背景。被否，因为代价永久、收益是想象的。
- **只支持 PostgreSQL**：会杀掉单人模式的核心体验（一个文件、`rm` 即清空、零服务）。否。
- **只支持 SQLite**：多用户下并发写与共享访问都不成立。否。
- **在 SQLite 与 PostgreSQL 之上做"一套 SQL 跑两边"**：会在 FTS、upsert、部分索引三处泄漏，最后既慢又难查。否——方言差异显式化才是可持续的。
- **PostgreSQL 用 `tsvector` + `zhparser`**：中文更准，但要求一个多数托管环境没有的扩展，且引入词干化伤害标识符匹配。仅在检测到扩展时作为增强路径。
- **引入 ORM 抹平方言差异**：GORM 表达不了 `FTS5 MATCH`、`bm25()`、部分唯一索引；ent 会让 schema 有两份描述并漂移。否。
