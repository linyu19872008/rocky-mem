# ADR-0008：语料层（source / chunk）

- 状态：已采纳
- 日期：2026-11-26
- 决策者：维护者
- 相关：[ADR-0002](0002-split-memory-and-experience-tables.md)（两张表）、[ADR-0007](0007-solo-only-scope.md)（只做单人）

## 背景

投喂（ingest）原本只有一条出口：把抽取出的文本截断 4000 字符，塞进一条 `proposed` 的 `howto` 经验——`symptom` 取首行、`fix_md` 取正文、`applies_when` 写「after human ingest review」。

这条路有三个问题：

1. **一篇文档被当成一条解法。** 上下文包的 `## Applies` 段会把那段正文渲染成「做法」，agent 会照着它执行。长文档的后半截被截掉，而前半截被当成结论。
2. **预览时已经分了块，确认时又丢掉。** `IngestPreview` 调 `extract.Chunk(text, 3500)` 只为数一个 `ChunkCount`，然后在 `IngestConfirm` 里被整个丢弃。
3. **设计里早就留了位置。** `search_doc.kind` 允许 `'chunk'`、包装配里有 `## Background` 段、`assemblePreferences` 的第三个参数是个空槽——全都空着。

## 决策

**把语料做成独立的一层：`source`（文档）+ `chunk`（片段）。** 投喂默认写语料，不再默认造经验。

具体十条：

1. **默认 `corpus` 模式**：只写 `source` + `chunk` + `search_doc`。`distill` 模式（额外生成一条待审经验）保留，但默认关，由确认页的复选框触发。
2. **语料不是证据**：`source` 不写 `raw` 行。`raw` 仍然只放「可引用的证据」。代价是无法直接表达「这条经验来自那份文档」，那是 `link` 的职责（尚未实现）。
3. **去重键是脱敏后全文的 hash**，不是文件字节 hash。同一文档另存一次不会产生第二份。
4. **重投喂同一 `uri` 且内容不同 → 旧 `source` 转 `archived`**，且**同时删掉它所有 chunk 的检索行**。否则检索会同时返回三个版本，而 agent 无从判断哪个是新的。
5. **chunk 存自己的文本副本**，不存指向 `raw` 的偏移量。SQLite 的 `substr` 对 BLOB 按字节、对 TEXT 按字符，PostgreSQL 按字符——中文下字节偏移和字符偏移差三倍，算错不报错，只是乱码。
6. **`## Background` 段承接语料，且有硬上限**：默认 2 条、每源 1 条、且只在剩余预算 ≥ 30% 时出现；显式请求 `kinds:["chunk"]` 时放宽到 5 条 / 每源 2 条。语料绝不能把经验挤出结果。
7. **默认 `kinds` 含 `chunk`**：agent 不会主动去要背景材料，所以默认给一点点。
8. **说清楚 `c_` / `s_` 怎么读**：`mem_get` 接受这两种 uid，`c_` 返回片段全文 + 源信息，`s_` 返回文档元数据 + 片段目录（不含全文）。
9. **`purge --source s_…`** 删文档及其全部片段；`reindex` 与 `doctor` 把 `kind='chunk'` 一并纳入。
10. **`search_doc.kind='chunk'` 从此有写入方**，`kinds:["chunk"]` 不再返回 501；`kinds:["source"]` 仍返回 501——文档是容器，只有它的片段被索引。

## 后果

**得到：**

- 长文档不再被压成一条假解法；正文完整保留，按块可检索。
- 「这个项目里哪份文档讲过 X」变得可回答，且带 `s_`/`c_` 出处。
- 同一文档重复投喂是幂等的；文档更新后旧版本自动退场。
- 检索质量有明确护栏：语料在 pack 里排最后、有数量上限、有预算门槛。

**放弃：**

- **存储翻倍。** 语料文本存两份（`chunk.text` + `search_doc.body`），PostgreSQL 侧生成列还会再存一份检索文本。接受：这都是派生层，`reindex` 可重建。
- **语料与经验之间没有硬关联。** 要知道「这条经验是从那份文档提炼的」，得等 `link`。
- **`source` 没有版本历史页。** 只有 `archived` + `superseded_by` 两个字段，看不到旧版本的片段内容。
- **`kinds:["source"]` 永远是 501。** 文档本身不参与检索，这是刻意的，但会让「我想搜文档名」的人困惑——`chunk` 的 title 里带了源标题，算部分补偿。
- **块边界只认 markdown 标题。** PDF/docx 的 `heading` 永远为空，`## Background` 里的条目会少一层定位信息。

**重新审视的条件**：若 `link` 落地，应把「经验 ← 文档」的关联补上；若评测显示 Background 段拉低 recall@10，则把默认 `kinds` 里的 `chunk` 去掉、改为显式 opt-in。

## 备选方案

- **继续把文档塞进 `experience`**：这就是现状，问题是它把背景材料伪装成结论，且截断。否。
- **chunk 存 `(raw_id, start, end)` 偏移**：省一份存储，但引入字节/字符偏移的跨方言陷阱，且每次读片段要多一次 raw 解引用。否。
- **把语料写进 `raw` 并当作证据**：会让「证据」和「背景材料」失去区分，`purge` 与导出语义也跟着浑浊。否。
- **默认不返回语料（只在显式 `kinds` 时）**：更保守，但 agent 不会主动要，等于「只存不用」。否。
- **每次投喂都同时 distill**：会制造大量低质待审经验，把审核队列变成噪音源。否，改为显式勾选。
