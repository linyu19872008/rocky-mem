## 背景

第一版面向单机单人：本地守护进程、Web 界面、MCP 客户端都在同一台机器上。问题不是"哪个数据库扩展性最好"，而是"哪个能让人在不请 DBA 的前提下安装、备份、检查、删除"。

最终比预期更重要的约束：

**数据量小。** 每用户年约 5 000 条经验、1 000 条记忆、20 000 条证据，加上原始证据约 400 MB。性能目标是 5 万条文档下检索 p95 ≤ 30 ms、写入 ≤ 20 ms。这不是苛刻的负载。

**并发只有一个写者。** MCP 客户端（Cursor、DSH）各自 spawn 子进程。若这些子进程直连数据库，就会是多个写者打一个单写者引擎。这是进程模型问题，不是存储引擎问题，且与选哪个引擎无关。

**必须能跑在 Windows 上。** 那里没有 Unix domain socket。

**FTS5 不保证存在。** Python 自带的 SQLite 可能未编译 FTS5，且系统构建常禁用可加载扩展。任何依赖它们的特性都需要探测和文档化的降级，而不是假设。

**迁移到 PostgreSQL 是可能的，但当时不在计划内。** 若日后变成团队部署，schema 不应重写——但不该为可能不发生的未来预付抽象税。

## 决策

**SQLite，WAL 模式，由单一守护进程独占。**

- 传输：loopback TCP（`127.0.0.1:7719`）+ `$ROCKYMEM_HOME/token` 里的 Bearer token，不用 unix socket。loopback 三平台可用，token 提供同等的本机访问控制。
- 所有访问经过守护进程。`mcp --stdio` 与 CLI 都是客户端。仅当守护进程未运行时，CLI 可进程内打开数据库，独占写者角色。
- 单写者：单一写入队列，写事务用 `BEGIN IMMEDIATE`，`busy_timeout=5000`。特意用 `BEGIN IMMEDIATE`：延迟事务从读升级为写时可能与另一读者死锁，表现为不可预测位置的 `SQLITE_BUSY`。
- 启动探测 `sqlite_version() >= 3.34.0` 与 `sqlite_compileoption_used('ENABLE_FTS5')`。失败则降级 `LIKE` 检索、界面横幅、`doctor` 报 `ERR_FTS_UNAVAILABLE`。降级必须被声明。
- 备份用 `VACUUM INTO` 在线快照——不锁库，且不能对 WAL 数据库直接 `cp`（那会得到损坏的备份）。

**由评审强制执行的移植性规则：**

1. 类型限于 `TEXT/INTEGER/REAL/BLOB`；不用 `DATETIME`、不用 `BOOLEAN`。
2. 时间是 Unix 纪元秒，存 `INTEGER`。
3. 不用 `AUTOINCREMENT`；内部 `INTEGER PRIMARY KEY`，对外 `uid` 由应用生成。
4. 检索藏在 `SearchIndex` 接口后。SQLite 实现用 FTS5 + trigram；PostgreSQL 实现会用 `tsvector` + `pg_trgm`。调用方看不到 `MATCH` 语法。
5. 触发器是 SQLite 适配器的内部细节。`reindex` 必须始终能从事实层重建派生层。
6. 导出用 JSONL，不做裸文件拷贝。

## 后果

**得到：**

- 单文件备份、任意 SQLite 工具可查、`rm` 即删除。对一个存放数月工作知识的系统，这是硬要求。
- 没有要装的服务、没有要开的端口、没有要管的凭据。
- 点查亚毫秒；全文路径有充足余量达成延迟预算。
- 整件事是可逆的：删掉一个目录就清空。

**放弃：**

- **永不允许并发写者。** 需要写的第二个进程必须经过守护进程。这是真实的架构约束，不是可调优的限制。
- **没有原生排序质量。** FTS5 `bm25()` 够用，但没有 `tsvector` 权重、没有 `pg_trgm` 相似度算子、没有 GIN 索引。
- **触发器是引擎特有的。** PostgreSQL 移植会用生成列或索引服务替换。
- **向量推迟。** `sqlite-vec` 需要加载扩展，而很多构建禁用了它。向量检索属于 P3 且可选；系统必须在不具备它时完整可用。
- **Windows 路径处理是我们的责任。** 不能硬编码 `~/.rockymem`；状态目录按平台解析。

**重新审视的条件**：若超过一台机器需要共享同一个存储，或有团队部署需求。届时 schema 已是 PostgreSQL 形状，移植等于重写检索适配器加一次 JSONL 数据迁移。

## 备选方案

- **第一天就上 PostgreSQL**：对一个在笔记本上工作的人是错的——要装服务、开端口、管凭据、管升级、管备份。用项目最大的采纳优势换取多年内用不上的容量。
- **DuckDB**：分析引擎好，单行 OLTP 差，增量全文能力不对等。本负载以小的点读与小写为主，正是 DuckDB 不擅长的。
- **磁盘上的 JSON 文件**：对零依赖叙事有吸引力，但每个查询都是全表扫描，原子更新变成要自己写的锁问题——重新发明一个更差的 SQLite。
- **嵌入式 KV（LMDB、sled）**：快，但索引、查询、迁移逻辑全变成我们的代码。SQLite 已经自带。
