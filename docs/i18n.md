# Internationalization

Two unrelated problems share one name. This document covers both, and the line
between them.

| | **A. UI localization** | **B. Content language** |
|---|---|---|
| Scope | finite, curated strings | unbounded user text |
| Mechanism | message catalogs + ICU | `lang` tag + cross-lingual retrieval |
| Translation | required | **never performed** |
| Failure mode | a missing key, a layout break | a wrong fact, a split source of truth |
| Effort | days | weeks |

Rule of thumb: if a change would require translating *stored data*, it is not an
i18n change, it is a data corruption.

---

## 1. Supported locales

| Locale | State | Notes |
|---|---|---|
| `en` | Source of truth | Fallback for every unresolved case |
| `zh-CN` | Complete | Simplified Chinese |
| `zh-TW` | Not shipped | Folder name reserved; `zh-Hant*` currently falls back to `zh-CN` — documented as a known limitation |
| `en-XA` | Test-only | Pseudo-locale: strings wrapped in `[[…]]` and inflated 40 % |

There is deliberately no bare `zh`. Bare `zh` is ambiguous between scripts, and a
locale named `zh` becomes impossible to split later.

## 2. Resolution

Applied server-side, once per request, before rendering.

```text
1. ?lang=<tag>                     explicit, for sharing and testing
2. setting.locale                  the user's saved choice (server-side)
3. Accept-Language                 browser/system, q-ordered
4. "en"                            fallback
```

`Accept-Language` matching uses **truncation**, not fuzzy best-fit:

```text
zh-Hans-CN  → zh-CN
zh-Hans     → zh-CN
zh          → zh-CN
en-GB       → en
en-US       → en
*           → en
```

`localStorage` is not part of the chain of authority. It caches the resolved
locale so the client can apply an instant switch, but the server value wins on
the next request.

Resolution happens **server-side** so that the first paint carries the correct
`<html lang>` and the correct catalog. Resolving on the client means a visible
flash of the wrong language, which is the most common visible i18n defect.

## 3. Message catalogs

```
web/locales/en.json              UI strings (source)
web/locales/zh-CN.json           UI strings (translation)
src/rockymem/i18n/locales/en.json       CLI and server-side human text
src/rockymem/i18n/locales/zh-CN.json
```

Backend catalogs exist for exactly one purpose: CLI output. The HTTP API and MCP
never return localized prose — they return `{code, params}` and the client
translates (`error-codes.md`).

### Key grammar

```
<domain>.<component>.<element>[.<variant>]
```

```json
{
  "review.queue.empty": "Nothing waiting for review.",
  "review.queue.action.approve": "Approve",
  "search.result.evidenceCount": "{count, plural, =0 {No evidence} one {# source} other {# sources}}",
  "entry.trust.active": "Active",
  "entry.trust.contested": "Contested",
  "error.ERR_EVIDENCE_REQUIRED": "This entry needs at least one evidence reference.",
  "error.ERR_ENTRY_CONFLICT": "This contradicts {count, plural, one {an existing entry} other {# existing entries}}."
}
```

Rules:

1. **ICU MessageFormat only.** No concatenation, no hand-rolled conditionals, no
   `${a} + ' ' + ${b}`. Word order differs between languages and concatenation
   makes translation impossible.
2. **No HTML inside messages.** Compose in the component.
3. **Every error code has `error.<CODE>`;** a missing key renders the raw code,
   never an empty string.
4. **Enum values are keys:** `entry.trust.<code>`, `entry.scope.<code>`,
   `entry.expType.<code>`, `entry.memType.<code>`.
5. **Keys are stable identifiers, not English sentences.** Renaming a key is a
   translation reset.

### Why ICU rather than a simple key-value map

Plural categories are not universal: English has `one`/`other`, Chinese only
`other`. A naive `"# item(s)"` leaks English grammar into every translation. ICU
also covers `select` (gender, formality) and number/date skeletons, which the
timeline and review queue both need.

## 4. Formatting

| Concern | Rule |
|---|---|
| Dates and times | `Intl.DateTimeFormat` with the resolved locale; storage is UTC epoch seconds; display is local time zone |
| Relative time | `Intl.RelativeTimeFormat` ("3 days ago" / "3 天前") |
| Numbers | `Intl.NumberFormat`; never assume `,` is the group separator |
| Lists | `Intl.ListFormat` ("a, b and c" / "a、b 和 c") |
| Sorting | `Intl.Collator` **client-side**. Never `ORDER BY title` in SQL: SQLite has no ICU collation, so Chinese sorts by code point, which looks like a bug |
| Percentages, file sizes | locale digits, but file sizes keep binary units (KiB) |

## 5. Layout and typography

- CSS logical properties only (`margin-inline-start`, not `margin-left`). Costs
  nothing now; makes RTL a configuration change instead of a rewrite.
- `<html lang>` is always set from the resolved locale; also set it on any
  subtree rendered in a different language (for screen readers and hyphenation).
- Budget **+40 %** width for translated strings. Pseudo-locale `en-XA` exists to
  prove it.
- Chinese text needs no inter-word spacing, but mixed CJK/Latin text benefits from
  small spacing; handle with CSS, not with inserted spaces in the catalog.
- Do not translate keyboard shortcuts. `a` / `e` / `r` / `s` in the review queue
  are physical keys and stay constant; only their labels are translated.

## 6. Content language (problem B)

### 6.1 Tagging

Every content row carries `lang`:

| Value | Meaning |
|---|---|
| `en`, `zh-CN`, … | Detected or declared language |
| `und` | Undetermined (very short text, code only) |
| `mul` | Genuinely mixed — "跑 `kubectl rollout restart` 之后 Pod 起来了" |

Detection runs after NFC normalization and before insert: CJK character ratio
above 15 % → `zh-CN`; mostly ASCII with English function words → `en`; both
substantial → `mul`. The author can override. `mul` is not a failure state — a
large share of real technical notes are mixed, and forcing a choice would corrupt
retrieval for both languages.

### 6.2 Never translate content

Three reasons, in order of severity:

1. **Two sources of truth.** A translated entry has its own evidence, its own
   trust state and its own conflict history. When one is updated, the other
   silently rots.
2. **Meaning changes.** "内存" is memory or RAM depending on context. A machine
   translation of a fix can invert its meaning.
3. **It is unnecessary.** Retrieval, not translation, is what makes a store
   usable across languages.

### 6.3 Cross-lingual retrieval

Three layers, shipped in this order:

**Layer 1 — one language-agnostic index (P0).** Trigram substring matching on
both backends: FTS5 with `tokenize='trigram'` on SQLite, `pg_trgm` GIN with
`ILIKE '%term%'` on PostgreSQL. Substring matching works for Chinese without a
dictionary and for exact identifiers (`Xid 69`, `ERR_CONN_REFUSED`) better than
any stemming tokenizer. A `LIKE` fallback is joined in when the query contains a
token shorter than three characters, because neither trigram implementation
indexes those. See `../design/schema.md` §5 and `../design/adr/0006-two-database-strategy.md`.

**Layer 2 — curated term expansion (P1).** `data/seed/term-map.zh-en.yaml`
becomes the `term` table. A query is expanded with translations at weight 0.7, so
original-language hits outrank bridged ones:

```text
"显存 崩溃"
  → (显存 OR VRAM OR "video memory" OR "GPU memory")
    AND (崩溃 OR crash OR OOM OR "out of memory")
```

The map is curated, human-maintained, and PR-friendly. Machine translation is
**not** used for expansion: it introduces semantic drift and silently widens
recall in ways that cannot be debugged. `rockymem term explain "<query>"` shows
exactly what was expanded, so a bad match is diagnosable rather than mysterious.

**Layer 3 — multilingual embeddings (P3).** `bge-m3`-class local model, optional,
behind the same search interface. This is the only layer that handles vocabulary
outside the term map.

### 6.4 Consequences to live with

- A Chinese query finds English entries only through the curated map until P3.
- `symptom_key` unifies entries across languages only when language-neutral
  tokens (error codes, paths, tool names) exist; otherwise it is language-scoped
  to avoid false merges. Cross-language conflicts therefore need a human or a
  `link`.
- User memory (`mem_context`) is usually the only place a language mismatch is
  noticed immediately, because it is read verbatim at session start.

## 7. MCP and the context pack

Permanent decisions:

- Tool names, parameter names, descriptions: English.
- Context-pack headings: `## Preferences`, `## Applies`, `## Do not use`,
  `## Background` — English, always.
- Entry *content* inside the pack: untouched, original language, with a `lang`
  marker on the item when it differs from the pack's default.

Rationale: stable headings keep prompt caching effective, keep evaluation
comparable across agents, and keep behaviour reproducible for an agent that has
no locale signal at all. The informational content is what the model needs; the
five words of scaffolding do not justify giving that up.

## 8. Documentation language policy

The rule is about **who reads the document**, not about which document matters
more. Design documents are written in Chinese by their maintainers; contracts and
engineering documents are in English because their readers are external
contributors and third-party clients.

| Layer | Location | Language |
|---|---|---|
| Design | `design/**` — `DESIGN.md`, `schema.md`, `adr/`, `README.md` | **Chinese** |
| Contract | `docs/**` — `mcp-tools.md`, `error-codes.md` | English |
| Specification | `docs/**` — `i18n.md`, `i18n-glossary.md` | English |
| Engineering | repository root — `README.md`, `CONTRIBUTING.md`, `SECURITY.md`, `CHANGELOG.md`, code comments, commit messages | English |
| Translation | `README.zh-CN.md`, future `docs/zh-CN/` | Chinese, may lag |

The directory split is the enforcement mechanism: a document's language follows
from where it lives, not from a judgement call each time. Rationale is recorded
in `design/adr/0004-i18n-ui-scope-vs-content-language.md` §7.

Two things stay English in every layer: **identifiers** (tool names, field names,
error codes, enum values, pack headings) and **commit messages**. A translated
identifier is a bug, not a localization.

The Chinese documentation commitment is deliberately narrow: README, quickstart,
and the design set above. A promise of full bilingual documentation that cannot
be maintained is worse than no promise, because readers cannot tell which parts
are stale.

## 9. Guarantees enforced in CI

| Check | Tool | Failure |
|---|---|---|
| Key parity across locales | `rockymem i18n check` | CI red |
| Every ICU message compiles | FormatJS compile step | CI red |
| Every error code has `error.<CODE>` | unit test over the registry | CI red |
| No hard-coded UI strings | `eslint-plugin-formatjs` | CI red |
| Typed message keys | generated TS types from `en.json` | build failure |
| Layout survives +40 % | `en-XA` visual regression | CI red |
| No SQL `ORDER BY title` | lint rule / review | CI red |

Missing translations are tolerated at runtime — the value falls back to the
English text. A missing *key* is not tolerated: it breaks the build.

## 10. Adding a locale

1. Copy `web/locales/en.json` to `web/locales/<tag>.json`; translate values only.
2. Copy the backend catalog likewise.
3. Add the tag to the supported list and to the truncation map.
4. Run `rockymem i18n check` and the pseudo-locale visual test with the new
   locale forced.
5. Check `i18n-glossary.md` for the canonical translation of domain terms
   before inventing new ones.

A locale with incomplete coverage can be shipped behind a "beta" label, but key
parity is still mandatory.
